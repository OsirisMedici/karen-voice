# Read-aloud engine research

Researched 2026-10-22 against repository revision `0d2af56de9347f0634cb24c020f0d9d7cacbcdc0` and primary documentation. This is a research handoff, not an implemented feature or runtime acceptance report. This delegated engine investigation added only this file and did not launch an app, speak audio, install dependencies, or invoke synthesis. See [the integration plan](T3_READ_ALOUD_PLAN.md) for the proposed workflow and acceptance criteria.

## Intended outcome and scope

The proposed outcome is that Osiris can listen to a T3 assistant reply through Karen Voice, choose a locally available voice and speed, pause or resume, and stop playback before dictating again. Read-aloud should reduce the need to watch the chat while keeping control of audible output. Success requires intelligible speech, responsive controls, reliable completion state, and no synthesized reply entering a dictation transcript or paste operation. These are proposed acceptance criteria, not user-tested product decisions.

This note covers the macOS speech engine and integration into the existing app. The parent task verified the existing T3 project and recorded Osiris's choice of manual shortcut reading. Its [integration plan](T3_READ_ALOUD_PLAN.md) proposes copied text as the first input path. No T3 transport, endpoint, subscription, or permission is assumed to exist. Cloud voice selection, custom voice training, audio export, and Windows/Linux speech engines are outside the initial recommendation.

## Recommendation

Use `AVSpeechSynthesizer` with installed macOS system voices, behind a small native adapter owned by Karen Voice. Apple explicitly directs developers from deprecated `NSSpeechSynthesizer` to `AVSpeechSynthesizer`. Apple's AVFoundation speech synthesis documentation says synthesis runs on the device without sending the text to a server. Voice downloads remain a separate online prerequisite. [Apple NSSpeechSynthesizer](https://developer.apple.com/documentation/appkit/nsspeechsynthesizer?changes=_6&language=objc), [Apple speech synthesis](https://developer.apple.com/documentation/avfoundation/speech-synthesis), [Apple voice installation](https://support.apple.com/guide/mac-help/change-the-voice-your-mac-uses-to-speak-text-mchlp2290/mac)

Prefer a separate Swift bridge for the first implementation because this repository already compiles and links Swift into Rust. Keep speech synthesis independent of the existing Apple Intelligence bridge and its hardware/OS checks. A direct Rust Objective-C adapter is also viable, with the ownership constraints below. This preference is an integration judgment based on the inspected source, not a compiled comparison.

`/usr/bin/say` is useful for an eventual narrow system diagnostic. It is a weaker production interface for coordinated pause, progress, cancellation, and recording safety. A successful `say` test would establish only that that command and voice work in that session, not that Karen Voice's bridge or T3 integration works.

## Current architecture and concrete integration points

The following observations come from the checked-out source, rather than earlier installation notes.

- [AGENTS.md](../AGENTS.md) requires functional React components, existing stores, Rust commands/events, i18next copy, and separation of dictation from assistant actions. A dictated sentence must never become an executable command.
- [Cargo.toml](../src-tauri/Cargo.toml) and [Cargo.lock](../src-tauri/Cargo.lock) use Tauri 2.11.5, Rust, CPAL recording, local recognition dependencies, and macOS `objc2` 0.6 with Foundation/AppKit 0.3 bindings. There is currently no direct `objc2-avf-audio` dependency. [tauri.conf.json](../src-tauri/tauri.conf.json) declares macOS 13.0 as the minimum system version. Apple's synthesized speech class is available from macOS 10.14, so its base availability fits that minimum. Newer optional voice APIs need their own availability checks. [Apple class availability](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer)
- [lib.rs](../src-tauri/src/lib.rs), around lines 190-220 and 650 onward, constructs recording/transcription/history managers, registers managed state, and collects typed commands through `tauri-specta`. Add a speech coordinator here rather than putting the native synthesizer in a React component.
- [actions.rs](../src-tauri/src/actions.rs), `TranscribeAction::start` and `stop`, starts capture, handles microphone readiness and feedback, finalizes recognition, and eventually schedules paste. Read-aloud must arbitrate with the start path before `tm.start_stream()` and `rm.try_start_recording()`. Do not attach speech playback to transcript completion or the paste path and assume that means a T3 assistant reply arrived.
- [managers/audio.rs](../src-tauri/src/managers/audio.rs) exposes `try_start_recording`, `stop_recording`, `cancel_recording`, `start_microphone_stream`, `stop_microphone_stream`, and readiness/cancellation generations. Recording states are `Idle`, `Recording`, and `Stopping`. Both `AlwaysOn` and `OnDemand` microphone modes exist; on-demand capture may also close lazily. `Idle` therefore does not prove that the input stream is closed.
- [audio_toolkit/audio/recorder.rs](../src-tauri/src/audio_toolkit/audio/recorder.rs), `Cmd::Start`, `Cmd::Stop`, and `ChunkDisposition`, drains and discards input while idle. A start can accept in-flight ring-buffer samples. `Stop` drains captured samples after a callback pause handshake and then resumes the underlying transport. This protects recording boundaries but is not an existing speech-playback exclusion mechanism.
- [managers/audio.rs](../src-tauri/src/managers/audio.rs), `apply_mute` and `remove_mute`, changes system output mute while recording if enabled, preserving the previous mute state. This is not microphone exclusion. `TranscribeAction::stop` unmutes before its asynchronous recording finalization, which can include `extra_recording_buffer_ms`. Starting read-aloud at shortcut release would therefore be unsafe.
- [audio_feedback.rs](../src-tauri/src/audio_feedback.rs) handles start/stop sounds. Speech should have a separate lifecycle so notification sounds cannot be mistaken for reply playback completion.
- [settings.rs](../src-tauri/src/settings.rs), [settingsStore.ts](../src/stores/settingsStore.ts), and generated [bindings.ts](../src/bindings.ts) are the existing persisted-settings and typed frontend access path. Speech voice/rate preferences belong in that pattern; playback state should remain transient. UI labels belong in `src/i18n/locales/*/translation.json`.
- [build.rs](../src-tauri/build.rs), `build_apple_intelligence_bridge`, already runs `swiftc -parse-as-library`, creates a static library, and links it into Rust. [apple_intelligence.rs](../src-tauri/src/apple_intelligence.rs) shows C ABI calls and explicit string/result ownership; [swift/](../src-tauri/swift/) contains the other side. This bridge currently compiles only for macOS Apple Silicon and concerns FoundationModels. Speech needs a separate macOS build path, including an Intel decision, rather than inheriting those restrictions or its synchronous generation behavior.

## Native engine capabilities

### AVSpeechSynthesizer

Create an `AVSpeechUtterance` from text, configure it, then enqueue it with `speak`. Retain one synthesizer for the playback lifecycle; Apple says the system does not retain it for the app. Its queue and `isSpeaking`/`isPaused` describe synthesis state, not whether the user actually heard sound. In particular, `isSpeaking` can remain true while paused. [Apple synthesizer](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer), [Apple isSpeaking](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer/isspeaking)

Voice selection should enumerate `AVSpeechSynthesisVoice.speechVoices()`, display name/language/quality, and persist the selected identifier. Resolve it with `init(identifier:)` for each playback; it returns `nil` if the voice is unavailable. A language-based initializer selects by BCP 47 code, not a guaranteed named voice. Prefer an explicit language-matched fallback with a visible explanation when a stored voice disappears. Do not hard-code a voice name or assume the macOS preferred voice, Siri voice, `say` voice list, and AVFoundation list are identical. The latter equivalences were not established by this research. [Apple voices](https://developer.apple.com/documentation/avfaudio/avspeechsynthesisvoice), [Apple identifier lookup](<https://developer.apple.com/documentation/avfaudio/avspeechsynthesisvoice/init(identifier:)>)

Apple documents downloading additional voices through Accessibility voice settings; they are unavailable until download completes. Settings labels vary by macOS release, with current documentation using Read & Speak and older systems using Spoken Content. Offer installed voices first and instructions for system-managed downloads. Do not silently download large voice assets or promise that every listed language has an installed voice. [Apple voice installation](https://support.apple.com/guide/mac-help/change-the-voice-your-mac-uses-to-speak-text-mchlp2290/mac)

Rate is a native floating-point value bounded by `AVSpeechUtteranceMinimumSpeechRate` and `AVSpeechUtteranceMaximumSpeechRate`, with a system default constant. Set it before enqueueing; later changes do not affect the queued utterance. This is not the words-per-minute interface of `say` or `NSSpeechSynthesizer`. A UI speed multiplier needs an explicit, tested mapping; it cannot be presented as an exact audio-duration multiplier. Apply changed speed to future utterances or deliberately restart the current segment with clear behavior. [Apple rate](https://developer.apple.com/documentation/avfaudio/avspeechutterance/rate)

Pause with `pauseSpeaking(at: .word)` for a normal control, or `.immediate` for an immediate interruption. Resume with `continueSpeaking()`, which has an effect only while paused. Stop with `stopSpeaking(at: .immediate)` when dictation needs priority; stopping removes unspoken queued utterances, so it cannot be resumed like a pause. Each control returns a Boolean, which the adapter must handle rather than optimistically updating the UI. [Apple pause](<https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer/pausespeaking(at:)>), [Apple resume](<https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer/continuespeaking()>), [Apple stop](<https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer/stopspeaking(at:)>)

Delegate callbacks expose start, pause, continue, finish, cancel, and text-range progress. Retain the delegate too because the synthesizer's delegate property is weak. Segment-level completion must be aggregated into message completion. Cancellation has an important gap: `didCancel` is not called for unspoken queued utterances or when stopping between utterances. Never depend on one cancellation callback per queued segment. Apple's final-utterance finish callback also ignores that utterance's `postUtteranceDelay`; that property cannot serve as an acoustic safety delay before reopening input. [Apple delegate events](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizerdelegate), [Apple weak delegate](https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer/delegate), [Apple cancellation exceptions](<https://developer.apple.com/documentation/avfaudio/avspeechsynthesizerdelegate/speechsynthesizer(_:didcancel:)>), [Apple final delay behavior](<https://developer.apple.com/documentation/avfaudio/avspeechsynthesizerdelegate/speechsynthesizer(_:didfinish:)>)

### NSSpeechSynthesizer

The older AppKit API offers available/default voice identifiers, voice assignment, words-per-minute rate, start, pause, continue, stop, and a completion delegate. Apple marks it deprecated and recommends AVFoundation instead. It can explain legacy integrations but offers no reason to make it Karen Voice's new engine. Do not interpret deprecation as removal or claim a measured voice-quality difference from this research. [Apple legacy API](https://developer.apple.com/documentation/appkit/nsspeechsynthesizer?changes=_6&language=objc)

### /usr/bin/say as a diagnostic

The macOS-provided `say(1)` manual was read locally with `MANPAGER=cat man 1 say`; `say` itself was not executed. The manual documents installed voice listing with `-v '?'`, voice selection with `-v`, words-per-minute rate with `-r`, input through stdin or `-f`, file output with `-o`, output-device selection, and nonzero failure exit status. It has no documented pause/resume control API. Source: Apple's installed manual, `man 1 say`, dated 2020-08-13 on this host. This source is local; an attempted archived Apple web manual URL was unavailable and is not treated as evidence.

For a later authorized diagnostic, a Rust subprocess could launch the absolute executable, pass validated options as separate arguments, pipe reply text through stdin, retain the child handle, and wait for exit. Do not interpolate reply text into a shell, put private replies in process arguments, or enable the manual's network-output option. Process signals are not equivalent to AVFoundation's speech boundaries or delegate lifecycle. No subprocess cancellation behavior, offline playback, voice inventory, or output routing was tested here.

## Tauri and Rust integration proposal

These are proposed interfaces and file locations, not existing commands.

1. Add `src-tauri/src/managers/speech.rs` or a similarly scoped coordinator. It owns message identity, playback generation, bounded segment queue, state, and recording exclusion. A native adapter handles speech methods and callbacks. Receive already-authorized plain reply text from the parent's eventual delivery adapter. A proposed input is `{requestId, threadId, messageId, revision, text, voiceId, rate}`; that does not establish any T3 contract.
2. Add typed command operations for voice enumeration, speak, pause, resume, stop, and state snapshot through the existing `tauri-specta` collection. Expose structured accepted/rejected results. Publish small state/progress events including request identity and generation, not the entire private reply. Tauri supports frontend commands, managed state, and native-to-frontend events; events are appropriate for small lifecycle updates. [Tauri commands](https://v2.tauri.app/develop/calling-rust/), [Tauri state](https://v2.tauri.app/develop/state-management/), [Tauri events](https://v2.tauri.app/develop/calling-frontend/)
3. For the preferred Swift route, use a separate `speech_synthesis.swift` and C ABI header following the existing build pattern. Keep a retained synthesizer/delegate on a serialized main-thread owner. Copy inbound text before asynchronous dispatch and copy callback payloads before returning across FFI. Define allocation/free ownership and callback-context lifetime explicitly; prevent Rust panics crossing the ABI. Link the relevant Apple audio framework and Foundation. Compile for the repository's supported macOS architectures with the existing deployment minimum. No FoundationModels, Apple Intelligence eligibility, or model download should be required for ordinary system voice synthesis.
4. For a Rust-only route, the maintained `objc2-avf-audio` bindings expose `AVSpeechSynthesizer` behind `AVSpeechSynthesis`. Published 0.3.2 docs show that the native object is neither `Send` nor `Sync`. Tauri `manage` requires `Send + Sync + 'static`, so a mutex does not make the native object suitable for arbitrary managed-state sharing. Store a thread-safe command handle in Tauri state and keep the retained Objective-C objects with their owner. Do not add unsafe `Send`/`Sync` implementations to bypass this. Exact Cargo features and lockfile compatibility require a compile check later. [Bindings](https://docs.rs/objc2-avf-audio/latest/objc2_avf_audio/struct.AVSpeechSynthesizer.html), [Tauri managed-state bounds](https://docs.rs/tauri/2.11.5/tauri/trait.Manager.html#method.manage)
5. Dispatch native operations through the serialized owner, using the existing app's `run_on_main_thread` pattern when appropriate. This is a conservative integration choice, not a claim that Apple universally declares this synthesizer main-thread-only. Keep capture open/close waits and playback-completion waits off the UI thread, and never hold the recording mutex while waiting for a main-thread callback. Tauri distinguishes asynchronous command tasks from synchronous main-thread commands and provides explicit main-thread dispatch. [Tauri command execution](https://v2.tauri.app/develop/calling-rust/#async-commands), [Tauri dispatch](https://docs.rs/tauri/latest/tauri/struct.AppHandle.html#method.run_on_main_thread)
6. Prefer finalized assistant messages initially. Normalize Markdown to readable prose deterministically, preserve meaningful numbers and negation, and define explicit handling for code, URLs, tables, and very long replies. Do not execute embedded markup, shell syntax, or assistant instructions. Hold segments in the app queue and submit one at a time to simplify cancellation and limit stale queued output. Dedupe by message identity and revision; accept no new segments from an invalidated generation.

For initial UX, use explicit Play, Pause/Resume, and Stop controls with visible state and installed voice selection. The parent plan scopes the first version to manual reading of copied text and proposes skipping code blocks by default. Direct thread selection and automatic reading remain outside that version.

## Recording-safe lifecycle

This proposed policy deliberately gives user dictation priority. It avoids depending on headphones, output muting, VAD, or unverified echo cancellation.

1. Serialize every speech request and dictation-start request through one coordinator. Use states such as `Idle`, `PreparingSpeech`, `Speaking`, `Paused`, `StoppingSpeech`, and `RecordingBlocked`. Assign an epoch to each playback so late native callbacks cannot revive canceled work.
2. When a reply arrives during active capture or `Stopping`, defer playback or reject it visibly. Never interrupt and discard a user's dictation merely to read a reply. Wait for the actual stop/finalization acknowledgment, including the configured trailing recording buffer, rather than shortcut release or the transcribing overlay.
3. Before playback, acquire a temporary recording exclusion and await a confirmed closed/suspended input path. The simplest first implementation closes the microphone stream even in AlwaysOn or lazy-close mode and reopens it later according to the existing preference. Do not persistently change the user's microphone setting. New manager-level coordination is required; calling `stop_microphone_stream` alone does not install an exclusion and may bypass action cleanup if capture is active.
4. Block or serialize all input-start routes while the exclusion is held. Ensure there are no stale input frames or streaming-ASR sessions that can consume speaker output. The inspected idle consumer discards samples, but its in-flight start behavior still needs a boundary test. If any gate or close operation fails, do not start speaking and pretend the microphone is safe.
5. Start the retained synthesizer only after input exclusion is acknowledged. Record actual `didStart` separately from request acceptance. Keep exclusion while paused, because resume can start sound again. Ordinary output volume/mute remains the user's choice; do not unmute the system to force speech audibility.
6. If the user requests dictation while speech is speaking or paused, invalidate queued speech, stop immediately, and establish terminal native state. Use control results, native state, and callback handling together. The documented absence of `didCancel` between utterances means a callback-only wait can hang. On an uncertain stop or timeout, keep capture blocked with a recoverable error instead of opening it while speech may continue.
7. After terminal playback, apply a measured acoustic/output-buffer settling policy before input can receive samples. Neither a finish callback nor a fixed guessed sleep proves that Bluetooth/output buffers and room echo have ended. An initial conservative delay is a test parameter, not a verified guarantee. Discard residual capture frames and reset recording-scoped state before a fresh dictation start.
8. Release exclusion exactly once on successful completion, explicit stop, rejected start, or a resolved error. Restore only the microphone state the coordinator temporarily changed. Do not restart speech automatically after dictation, replay canceled messages, or override a subsequent user change to microphone mode. On quit/device loss/sleep, invalidate work and clean up ownership; after wake, require a fresh state check.

## Local versus cloud tradeoffs

Native system voices are the recommended baseline because Apple documents on-device synthesis, and Karen Voice already contains native macOS bridges. Once a chosen voice is available locally, the intended path needs no cloud TTS account, API key, or per-request service integration. Verify operation with networking unavailable before calling the feature offline-ready. Apple-managed voice installation can require connectivity and disk space. [Apple on-device synthesis](https://developer.apple.com/documentation/avfoundation/speech-synthesis), [Apple downloads](https://support.apple.com/guide/mac-help/change-the-voice-your-mac-uses-to-speak-text-mchlp2290/mac)

A cloud alternative would send the selected reply text to a provider and require separate decisions about authorization, retention, cost, latency, credentials, and cancellation of both generation and playback. It may offer useful voices, but no provider was evaluated here and no quality advantage is established. Treat it as a later explicit opt-in with no silent fallback. Local TTS does not make the original T3 conversation local, prevent other applications recording system sound, or prove that the rest of Karen Voice avoids network traffic.

Do not add a local generative TTS model before testing whether installed Apple voices meet the outcome. Its model weights, runtime, memory use, packaging, and licensing would be additional work without demonstrated need.

## Verification still required

Repository inspection and documentation establish plausible integration, not a usable feature. AVFoundation voice enumeration, audible playback, network isolation, a native bridge build, microphone exclusion, and paste behavior remain unverified. Machine-specific speech probe evidence is omitted from this public source checkpoint.

Before acceptance, a future implementation should demonstrate all of the following:

- Build and launch the exact app on each supported macOS architecture and deployment range. Check Swift framework linking, FFI ownership, delegate lifetime, and the Rust alternative's exact features if selected. No compatibility claim follows merely from matching base API availability.
- Enumerate real AVFoundation voices, select one, persist/re-resolve its identifier, and handle a missing/deleted voice. Speak fresh text after relaunch with networking unavailable and the voice already installed. Listen for intelligibility in the intended language, technical words, and longer replies. Siri/Personal Voice availability and parity with system settings remain unverified. Personal Voice is optional and has its own authorization API, so exclude it from the baseline. [Apple Personal Voice authorization](<https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer/requestpersonalvoiceauthorization(completionhandler:)>)
- Exercise pause/resume/stop before start, during words, between segments, during delays, while paused, and after completion. Verify request identity, duplicate suppression, cancellation without `didCancel`, and late callbacks. Measure actual stop latency rather than describing it as instantaneous acoustic silence.
- Test dictation interruption with speakers and headphones, OnDemand, AlwaysOn, lazy close, both mute settings, trailing recording buffers, streaming recognition, rapid shortcut repetition, missing microphone permission, and device reconnects. Confirm the synthesized reply never appears in transcript, history, or paste, and that legitimate dictation still works afterward.
- Test user-muted output, output-device changes, Bluetooth latency, sleep/wake, app quit, and restart. A successful synthesis callback is not audible-output proof. Several generic AVFoundation docs mention audio-session routing APIs; their availability and behavior must be checked on native macOS before reusing iOS routing examples.
- Once the parent establishes reply delivery, verify that exactly the intended finalized assistant reply reaches Karen Voice, with no historical replay, wrong-thread speech, partial-token duplication, or read-aloud loop. This research establishes none of that transport behavior.

No release, installed-app, first-launch, or dictation acceptance status is asserted here. For later implementation checks, follow [BUILD.md](../BUILD.md) and the repository's native acceptance requirements.
